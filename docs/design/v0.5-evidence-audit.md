# v0.5 — what Evidence is today, and what first-class would cost

The audit the v0.5 brief asks for before any code is written. It answers five
questions: what the current representation is, where it is read and written,
whether `eid` is sufficient for reuse, where Source / Evidence / Interpretation
are ambiguous, and what a migration would risk.

**One architectural conflict is reported at the end.** It is the reuse
requirement (§6), and it needs a decision before that part is built. Everything
else in the brief can proceed without it.

## 1. What an Evidence record is today

`frontmatter::Citation`, stored in the citing note's own frontmatter under
`sources:`. A vault file looks like this:

```yaml
---
id: 01HQ3M8K2P00000000000000A1
type: literature
title: Reading Singh 2023
sources:
  - eid: 01HQ3M8K2P00000000000000E7
    id: 01HQ3M8K2P00000000000000S3 # the Source note
    page: "S12"
    quote: "films grown at 350 °C show…"
    kind: experimental
    captured: 2026-09-14T13:00:00Z
    annotation: ZAB12CD3 # Zotero's annotation key
    colour: "#ffd400"
    comment: "only two samples" # the researcher's remark
---
```

Against the brief's §1 field list, the record already carries: `eid`, source
note id, annotation key, exact quoted text, a page label, evidence type,
researcher comment kept separate, colour as inert metadata, and a `captured`
timestamp.

Three of the brief's fields are **absent**:

| Field                                                 | Status                                                                                                                                                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Zotero item key                                       | Not on the record. Reachable as `source.source.zotero` — one hop through the Source note, which is the right place for it: the item key is bibliographic, and the Source note is the bibliographic record. |
| PDF page index                                        | Not stored. The reading pane knows it at capture time (`data-page`) and discards it, keeping only the printed label.                                                                                       |
| `origin` (manual / PDF selection / Zotero annotation) | Not stored, but **derivable today**: an `annotation` key means it came from Zotero; otherwise it was typed or selected. The two non-Zotero origins are not distinguishable.                                |

Adding all three is additive and carries no migration risk — every key on this
struct is already `#[serde(default, skip_serializing_if)]`, which is the
pattern that let v0.4 add `annotation`, `colour` and `comment` to v0.3 notes
without touching a byte of them.

## 2. Everywhere it is read or written

**Written — four places, all in `vault.rs`:**

| Site                                  | What it does                                                                                |
| ------------------------------------- | ------------------------------------------------------------------------------------------- |
| `set_citations`                       | Replaces a note's whole list. Mints an `eid` for any entry lacking one; preserves the rest. |
| `capture_annotations`                 | Additive, idempotent by Zotero annotation key. Never deletes.                               |
| `create_literature_note`              | Writes the single citation linking the new note to its Source.                              |
| `import_source` / `merge_source_meta` | Touch `source:`, not `sources:`.                                                            |

**Read:** `summary_of` (every note listing), `index.rs` (`note_sources`), the
export path, `SourcesPanel`, `Bibliography`, `citationStore`, `provenance.ts`,
`ResearchOverview`.

**The derived index knows almost nothing about evidence.** The only table is:

```sql
CREATE TABLE note_sources (source_id, note_id, page, PRIMARY KEY (…));
```

No `eid` column. No quote. So SQLite cannot answer "which notes use evidence
E?" or "find the evidence whose text contains X" — both required by §5. This
is a gap to fill, not a conflict: the index is explicitly derived and
rebuildable, so adding an `evidence` table costs a schema bump and a reindex
and nothing else.

## 3. Is `eid` sufficient for reuse?

**As an identifier, yes. As an address, no.**

`eid` is a ULID, minted once and preserved across edits — `set_citations`
mints only into an empty slot, and a test asserts that a record sent back
keeps the id it had. It survives moves, renames and reindexing, because it
lives in the file.

What it cannot do is be _found_. Nothing resolves an `eid` to the note holding
it; locating evidence E means scanning every note's frontmatter. And nothing
can point _at_ one: there is no syntax for "this interpretation rests on E7".

Both are fixable in the derived index without touching the file format.

## 4. Source / Evidence / Interpretation, and where they blur

| Concept               | How it exists today                                                  | First-class?                 |
| --------------------- | -------------------------------------------------------------------- | ---------------------------- |
| **Source**            | A note, `type: source`, with `source:` metadata                      | Yes                          |
| **Evidence**          | A frontmatter entry inside the note that uses it                     | Identified, not addressable  |
| **Interpretation**    | A **markdown heading** in a note body, recognised by `voiceRules.ts` | **No — it has no id at all** |
| **Research Question** | Both: a `question` note type, _and_ a heading voice                  | Ambiguous                    |

Two ambiguities worth naming:

**Interpretation is prose, not an object.** `voiceOf("My interpretation")`
classifies a heading; the text under it is paragraphs. §7 asks for a stable
link from an Interpretation to the Evidence it rests on, and there is nothing
on the Interpretation side to attach that link to. This is a second structural
gap, independent of the reuse one.

**A Question is two different things.** A note can be `type: question`, and a
heading inside any note can be the question voice. The research overview reads
the headings; the note type is separate. §8 needs one of them to be the thing
Evidence points at.

**What is _not_ ambiguous, and must stay that way:** `quote` is the source's
words and `comment` is the reader's, kept in separate fields, never merged —
the v0.4 annotation import exists largely to preserve that split. Nothing in
v0.5 should weaken it.

## 5. The conflict: reuse across notes (§6)

> "One Evidence object may support multiple notes or interpretations. Do not
> duplicate quoted evidence merely because it appears in two notes."

**An Evidence record is owned by the note that cites it.** That is the whole
storage model: `sources:` is a key in one note's frontmatter. There is no
place a record can live that is not inside exactly one note.

So one quote used by two notes has three possible shapes, and each costs
something:

**A. Copy it into both notes.** What happens today. Two files carry the same
`eid` with independently editable text — precisely the second source of truth
the brief forbids. Edit the quote in one and the vault now disagrees with
itself about what the paper says. Rejected.

**B. One note owns it, the other holds `{eid}` only.** No duplication, but it
makes one ordinary note authoritative over another's provenance. Delete or
archive the owning note and the reference dangles — a literature note silently
loses the quote its argument rests on because an unrelated note was tidied
away. Rejected.

**C. Evidence gets a home of its own.** A record lives in one place that is
_about_ that evidence, and notes reference it by `eid`. Markdown stays
authoritative, there is exactly one writable copy, and nothing depends on
another note's lifetime.

**C is the only shape that satisfies the brief**, and it is the same move the
project already made for Source: a paper is cited rather than written, so it
became its own note. Evidence is quoted rather than written; the argument is
identical.

It is still a model change, so it needs your decision on _where_ that home is:

|        | Where a record lives                        | Reads as                                                                                 | Cost                                                                                                                                                                                        |
| ------ | ------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **C1** | A note of a new `type: evidence`            | Fits the existing model exactly — evidence is browsable, linkable, backlinkable for free | One note per quote. A paper read closely becomes thirty notes in the list, which needs the note list to learn to hide them, as it already does for `source`                                 |
| **C2** | An `evidence:` block on the **Source note** | Evidence sits with the paper it came from; one file per paper, however many quotes       | Source notes become large. Two notes capturing from one paper write to the same file — the concurrent-write path that `write_atomic` and the sync tests already cover, but on a hotter file |

**Recommendation: C2.** Evidence belongs to the paper, not to the reader's
filing. It keeps one file per paper rather than one per sentence, it puts the
quote next to the bibliographic record that gives it meaning, and a Source
note is already the thing both readers of a paper share. C1's advantages are
mostly incidental (backlinks, browsing) and are things the Evidence browser in
§5 has to build anyway.

**Backwards compatibility under either.** Inline `sources:` entries stay valid
and keep working, unmigrated, forever. An `eid` is owned by exactly one place —
inline in a note, or by an Evidence record — never both, so no second source of
truth is created. Promoting an inline record to a shared one is an action the
researcher takes when they want to reuse it, not a migration that runs over
their vault.

## 6. Migration risk list

| #   | Risk                                                                                                                                            | Severity                                                                                                                                                                         | Mitigation                                                                                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Two copies of one `eid` become editable independently                                                                                           | **High** — the failure the brief names                                                                                                                                           | An `eid` is owned by exactly one place. A completeness check (§9) reports any duplicate rather than picking a winner                            |
| 2   | `set_citations` replaces the whole list and mints an `eid` into any empty slot, so a caller that drops one silently re-identifies that evidence | Medium. **Latent, not live**: every path in today's UI spreads the existing entry, and `ReadingPane` says so in a comment. It goes live the moment anything points _at_ an `eid` | Reject a write that drops an `eid` present on disk, rather than minting over it. Worth doing before §7, which is what makes the id load-bearing |
| 3   | Interpretation has no id, so §7's links have nothing to attach to                                                                               | **High**                                                                                                                                                                         | Decide the Interpretation object before building §7. Flagged in §4 above                                                                        |
| 4   | Source notes grow large under C2; two notes capture from one paper at once                                                                      | Medium                                                                                                                                                                           | Existing atomic-write and sync-rewrite tests cover the path; extend them to concurrent evidence appends                                         |
| 5   | Index schema bump forces a full reindex on first launch                                                                                         | Low                                                                                                                                                                              | Already routine — the index is derived, disposable, and rebuilt on mismatch                                                                     |
| 6   | Old notes read by a new build, or new notes by an old one                                                                                       | Low                                                                                                                                                                              | Every added key is `skip_serializing_if`; this is how v0.4 added three keys to v0.3 notes with no rewrite                                       |
| 7   | Export leaking ULIDs into a manuscript                                                                                                          | Medium                                                                                                                                                                           | §11 forbids it. Export tests must assert no `eid` appears in DOCX output                                                                        |

## 7. What can start now, and what is blocked

**Not blocked — no model change needed:**

- §1 additive fields: Zotero item key, PDF page index, `origin`
- §2 evidence types: the eight the brief names, chosen by hand, never inferred
- §3 the quote/comment split: already correct, needs tests that hold it
- §4 capture from PDF selection and Zotero annotations: v0.4 does this
- §9 completeness checks: deterministic, read-only, report-never-repair
- §13 the test list, for everything above
- Risk 2 above — cheap now, and it is the foundation §7 stands on

**Blocked on your decision:**

- §6 reuse — C1 or C2
- §7 Interpretation → Evidence — needs the Interpretation object defined
- §5 the Evidence browser and §10 citation ↔ evidence both read whatever §6
  decides, so they follow it
