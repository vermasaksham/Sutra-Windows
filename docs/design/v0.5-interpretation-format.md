# §7 interpretation blocks — format foundation

Status: proposed format with a fixture-tested codec and an experimental TipTap
container. App registration, creation controls, evidence selection, resolution
and export are still pending. No app path writes this syntax yet. This starts §7 from
[ADR 0005](../decisions/0005-evidence-as-an-object.md).

## Representation

An interpretation is Markdown prose inside a versioned fenced block:

````markdown
~~~sutra-interpretation-v1 {"iid":"01HQ3M8K2P00000000000000A1","evidence":["01HQ3M8K2P00000000000000E7"]}
## My interpretation

The result supports anisotropic growth, but only two samples were measured.
~~~
````

`iid` identifies this interpretation independently of its heading, location and
prose. `evidence` contains evidence ULIDs explicitly chosen by the researcher.
It may be empty. Neither the parser nor writer invents IDs, resolves references,
copies quotations, deduplicates entries or infers support from nearby citations.
Unknown metadata keys survive reading. Unknown evidence IDs and duplicate IDs
also survive; reporting them belongs to resolution and completeness checks.

A normal fenced block was chosen because an editor without this extension can
display it as literal text without interpreting the metadata as prose or losing
its body. Older Sutra builds have not been tested with this format: no backwards
editor compatibility is claimed until that path has its own test.

## Grammar and preservation

- The opening starts at column zero with at least three tildes or backticks,
  immediately followed by `sutra-interpretation-v1`, whitespace, and a JSON
  object on that same line. It must end with LF or CRLF.
- The object requires `iid` (a canonical uppercase ULID) and `evidence` (an
  array of canonical uppercase ULIDs). Other keys are retained verbatim.
- The closing fence uses the same character and at least the opening length.
  It may have up to three leading spaces and trailing spaces or tabs. It may
  end at EOF. Backtick-fence info strings cannot contain backticks.
- The body is opaque Markdown, including whitespace, line endings, chemistry,
  citations and code examples. Reading and writing an unchanged block preserves
  every byte, including metadata spacing and both fences.
- Explicit creation uses a tilde fence longer than any closing-fence-shaped
  line in the supplied body. It adds a final newline when needed to separate
  the body from the closing fence. It never rewrites the supplied prose.
- Future versions, malformed metadata and unclosed blocks are not interpreted.
  The caller must leave them as ordinary code blocks. It must not strip markers
  or mint replacement IDs.

The codec reads one token at the beginning of its input. It is **not a document
scanner**. The future editor integration must call it through the Markdown block
lexer, so fenced examples, block quotes and list nesting cannot accidentally
become live interpretations. Nested interpretation containers are not introduced
by this slice.

## Experimental integration and enablement gates

`src/editor/interpretation/Interpretation.ts` is an editable TipTap container,
deliberately **not registered** in `extensions.ts`. Tests use the same extension
vocabulary as the editor/export parser, plus this experimental node. They cover
MarkdownManager parsing/serialization and a ProseMirror schema round trip,
including prose edits, moves, unknown metadata and untouched LF framing.
These are headless fixtures, not browser editor or real-vault verification.

Three tests use `it.fails` to keep reproduced safety gaps executable. They are
**known failures, not passing feature verification**:

1. The Markdown lexer normalizes CRLF before the custom tokenizer sees it.
   The standalone codec preserves CRLF; this integration does not yet.
2. The lexer recursively recognizes a fenced block inside a blockquote as an
   interpretation. A quoted example must not create another live identity.
3. Ordinary code-block fallback rewrites unsupported-version fences. With
   embedded backticks this can also change how the saved document parses.

The current raw snapshot is an in-memory preservation aid, never a second
durable copy. When prose is edited, serialization retains metadata but uses
the editor's normal Markdown renderer for the changed body. No IDs are minted.
HTML paste is intentionally not recognized; identity semantics for copy/paste
and duplicate blocks must be settled before registration.

## Next slice and verification boundary

First close the three executable preservation/context gates above, and cover
nested interpretations, lists, copy/paste and undo in the browser. Then register
the container and add explicit controls to create a block and select supporting
evidence. Keep unrecognised versions readable and lossless.
Test actual editor open/edit/save/reopen behaviour and the shared export parser
before enabling creation. No existing heading is automatically converted.

Tests exercise the codec and experimental headless integration only. They do
not establish browser editor round-trip behaviour, real-vault use, evidence
resolution, indexing or export provenance.
