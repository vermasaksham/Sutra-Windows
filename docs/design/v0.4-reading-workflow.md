# Reading a paper, and capturing what it says

Status: **workflow decided. Not implemented.** The three questions this
document ended on are answered in [Decided](#decided); the body above them is
the proposal as approved.

The backend of v0.4 is done (`docs/decisions/0004-reading-the-paper.md`). This
proposes the workflow on top of it, and settles it before any UI is written.

Target workflow:

```
Zotero source  →  PDF  →  page-aware reading  →  select  →  Evidence  →  Interpretation
```

## The constraint everything follows from

**Sutra has no PDF renderer, and this proposal does not add one.** The backend
extracts _text_, page by page. It does not rasterise, lay out, or show a page as
the publisher drew it.

That is not a gap to fill later. A renderer is a large dependency, a second
document model, and the beginning of exactly the "separate PDF-management
system" this is not to become. Zotero already has an excellent reader, and
`Open in Zotero` already exists.

So the division of labour is:

| For                                                        | Use                      |
| ---------------------------------------------------------- | ------------------------ |
| Reading a paper as a document — figures, layout, equations | **Zotero's reader**      |
| Finding a sentence and capturing it with its page          | **Sutra's reading pane** |

The reading pane is a **capture surface, not a viewer**. Saying so plainly in
the UI is part of the design, not an apology for it.

## Where reading starts: the Source note

The Source note already carries a `PDF` row that reads `PDF — in Zotero`. It
becomes the entry point, and gains one action:

```
PDF            PDF — in Zotero          [ Read text ]  [ Open in Zotero ]
Annotations    6 in Zotero, 4 imported  [ Review ]
```

Nothing else moves. The Source note stays what it is — the paper's identity
record — and gains a way in to the paper's contents. No library, no file
manager, no import queue.

A PDF attached inside the vault shows the same row with `PDF — in this vault`
and the same `Read text` action. One code path, as the roadmap requires; the
only difference visible to the reader is a word.

## The reading pane

`Read text` opens a pane over the note list — not a new window, not a new
route. It is transient: closing it leaves nothing behind.

```
┌ Zhou 2019 — reading text ──────────────────── [Open in Zotero] [×] ┐
│  Text extracted from the PDF. For figures and layout, read it in   │
│  Zotero.                                                            │
│ ─────────────────────────────────────────────────────────────────── │
│  p. 431                                                             │
│  Sb2Se3 crystallises in a quasi-one-dimensional structure in        │
│  which [(Sb4Se6)n] ribbons are held together by van der Waals…      │
│                                                                     │
│  p. 432                                                             │
│  …                                                                  │
└─────────────────────────────────────────────────────────────────────┘
```

- **Page provenance is structural, not decorative.** Every page begins with its
  own heading, and text cannot be shown without one. A selection therefore
  always knows its page, because the page is the container it sits in.
- The heading shows the **printed label** where Zotero supplied one and the
  position otherwise, marked as such: `p. 431` versus `sheet 3`. ADR 0004's
  distinction, surfaced rather than hidden — a citation needs the printed
  number, and an invented one is worse than none.
- Extracted text is presented as **the source's voice** throughout, using the
  existing `.sutra-voice-*` treatment. Nothing in this pane is ever the
  reader's words.

## Selecting text becomes Evidence

Select, and one control appears at the selection:

```
    ┌──────────────────────────────┐
    │  Capture as evidence   p. 431│
    └──────────────────────────────┘
```

Pressing it writes one `sources:` entry and closes nothing — capture is
additive and repeatable, so a page can be mined in one pass.

What is written:

| Field      | From                           |
| ---------- | ------------------------------ |
| `eid`      | minted                         |
| `id`       | the Source note                |
| `page`     | the page the selection sits in |
| `quote`    | the selected text, **exactly** |
| `captured` | now                            |

`comment` and `kind` are left empty. **Interpretation is a second, deliberate
act** — the reader adds it in the evidence entry or writes it in their prose,
and the capture step never puts words in their mouth. That is the
Source → Evidence → Interpretation sequence made literal: you cannot capture an
interpretation by accident, because the capture control does not collect one.

## Zotero annotations

`Review` opens the same pane in a second mode — the annotations the researcher
already made, in reading order:

```
  p. 431   ▍ "ribbons are held together by van der Waals forces"     ● #ffd400
           ▸ your note: is this consistent with Zhou's fig. 3?
           [ Capture ]

  p. 433   ▍ "carrier lifetime of 1.2 ns"                    ✓ already captured
```

- **Quotation and comment are drawn differently and never adjacent-as-equals.**
  The highlighted text uses the source voice; the researcher's note is indented
  under `your note:` in the interpretation voice. This is the one thing the
  whole import must not blur, and it must be visible at a glance, not on
  inspection.
- **Colour is shown as a dot and means nothing.** No grouping by it, no
  filtering, no sorting, no inferred kind — see ADR 0004. It is there because
  the researcher chose it.
- **Already-imported annotations are marked `✓ already captured`** and their
  `Capture` control is absent. The backend matches on Zotero's annotation key,
  so this is exact rather than heuristic, and re-importing a paper after
  annotating it further shows only the new marks as actionable.
- A `Capture all new` control at the top, since importing a re-read paper is the
  common case. It reports what it did: `4 captured · 2 already here`.

## Where evidence lands

**Recommendation: the note the reader is working in — normally the Literature
note — and never the Source note.**

This is the existing model, not a new rule. `sources:` records what _this note_
rests on. A Source note is the paper's identity record; if evidence accumulated
there, two notes reading the same paper for different purposes would write into
one shared list, and `eid` would stop meaning "this reading of that paper".

Two consequences, both accepted deliberately:

- Two notes quoting the same sentence produce two evidence entries, with
  different `eid`s. That is correct: they are two readings, and either can be
  edited or dropped without touching the other.
- Capture needs a target note. Reading from a Source note with nothing else
  open, the pane says so and offers the existing action: _Literature note_ —
  which already creates a note about the paper that cites it. Reading is not
  blocked by this; only capturing is.

**A dedicated evidence view is rejected as a store and accepted as a lens.** A
separate place evidence _lives_ would be a second source of truth outside the
markdown, which the architecture forbids. A read-only view that _queries_
evidence already in notes breaks nothing — the research overview is already
this shape — and can come later without changing any of the above.

## When it does not work

Five states, each named, each leaving the bibliographic half untouched. A
source note, a citation and a bibliography never depend on a file.

| State                           | What the Source note's PDF row says                              | Actions                                  |
| ------------------------------- | ---------------------------------------------------------------- | ---------------------------------------- |
| **Zotero PDF, path unresolved** | `PDF — in Zotero. Sutra cannot open it yet.` with a one-line why | `Open in Zotero`                         |
| **No PDF**                      | `No PDF`                                                         | — (not an error; most sources have none) |
| **File missing**                | `PDF — in this vault, but the file is not there`                 | —                                        |
| **No text layer**               | `This PDF is a scan — no text to select.`                        | `Open in Zotero`                         |
| **Parser failed**               | `Sutra could not read this PDF.` plus what the parser said       | `Open in Zotero`                         |
| **Zotero unavailable**          | annotations row reads `Zotero is not running`                    | vault-attached PDFs still read           |

Two rules across all of them:

1. **Never "no PDF" for a problem that is not that.** An unresolved path and an
   absent file are different sentences, because they send a person to different
   places.
2. **`Open in Zotero` survives every failure.** Whatever Sutra cannot do,
   handing the paper to the program that owns it always works.

## What this proposal does not add

No PDF renderer, no thumbnails, no file library or PDF manager, no OCR, no
summarisation, no semantic search, no cross-note evidence store, no thesis-level
features. The reading pane opens from a Source note, captures, and closes.

## Decided

**1. A column beside the note, not a pane over the list.** Reading and writing
are visible together, which is the point of capture-while-writing.

This has a consequence that only appears once the real widths are read, and it
changes which column gives way. The window already carries four regions — rail
13rem, list 19rem, context panel 20rem — which is 832px of chrome before the
note gets anything, and `useWideEnough` already hides the context panel below
1280px for exactly that reason. A literal _fifth_ column would need about
1600px before the note column is usable, so on a laptop the reading column
would simply never appear. Something has to yield:

| Option                                 | At 1280px                      | What is lost while reading                                   |
| -------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| Reading **replaces the context panel** | fits                           | **Sources** — the evidence being captured, as it accumulates |
| Reading **replaces the note list**     | fits, same note width as today | the list of other notes                                      |

**Chosen: the reading column takes the note list's place**, and the context
panel stays. Reading one paper is precisely when the list of every other note is
least useful, and it is precisely when watching **Sources** grow is most useful
— the Source → Evidence loop is then visible end to end in one window, which is
the workflow this release exists to make real. The list returns when the reading
column closes; nothing is destroyed, and the reader's preference for the context
panel is untouched.

Below 1280px the same rule as today applies: the context panel goes first, and
reading and the note share what is left.

**2. No bulk capture.** `Capture all new` is not built. Every annotation is
chosen deliberately, one at a time. The convenience was real and the risk is
worse: bulk import is the fastest way to fill a note with evidence nobody has
actually read, and a provenance record whose entries were never considered is
indistinguishable from one that was — which makes every entry in the vault worth
slightly less. Re-reading a paper with twenty new highlights is a slower job
than it could be. That is accepted.

**3. Capture does not insert `[@ref]`.** Capturing evidence records it in the
note's frontmatter and nothing more. Nothing in Sutra writes into the reader's
prose without being asked, and that is not weakened for a convenience. The
citation is inserted by typing `@` where it belongs, which is a decision about a
sentence and belongs to the person writing it.

This leaves capture and citing as separate acts, and the **citation consistency**
panel already exists to notice when one has happened without the other — a
source recorded but not cited is reported there, which is the right place for it:
a half-written paragraph looks exactly like an omission, and Sutra says what
disagrees rather than fixing it.
